First, the vocabulary

Four words used constantly below — the rest doesn't parse unless these are clear.

cycle
The team's sprint. Two weeks long. Cycle 11 is the current one and closes on the 10th. Cycle 12 runs from the 10th to the 24th. "Move it to 13" means: not these two weeks, the next two.
point
The unit of effort the team estimates with. Not exact hours — relative size. 1 point is an afternoon; 5 points is several days. They exist so nobody commits to more than fits in two weeks.
carryover
A ticket that was in the current cycle, didn't finish, and therefore drags into the next one. It eats capacity of cycle 12 even if it isn't formally listed there.
epic
A container ticket. Not work itself: it groups the tickets that together ship a product capability. It shows up assigned in the tracker but has no points and is never implemented.

What we're building

Two different things, for two different users, in two different repos. That's the starting point of everything below.

Front A — the CSV export in the admin

acme-admin · user: the customer's admin · 6 points

The admin opens a report and downloads it to share with their compliance team.

today

Export is synchronous: the browser hangs until the file is ready, and anything over ~5,000 rows times out. Large customers email support, and support runs the query by hand.

after

Export becomes a background job with an email link when ready. Any size works, the browser never hangs, and support stops running manual queries.

The metric: manual export requests reaching support drop to zero.

Front B — search in the main app

acme-app · user: the end customer · 8 points

The customer types into the search bar to find a record.

today

Search only matches exact prefixes of the title field. A typo, a middle word, or searching by owner returns nothing — with no explanation.

after

Search matches across title, owner and tags, tolerates typos, and the empty state says what was searched and suggests the closest match.

The metric: the share of searches that end with zero results and no follow-up click.

This alone is a finding. Two fronts of near-equal weight, in two repos, for two users, on one developer for two weeks — that's a planning problem, not a detail. The decisions below are, at bottom, how to end up with one primary front and one secondary instead of two equal ones.

Ticket by ticket, in plain words

What each one does, what the user sees when it's done, and its real state.

Front A — the export

  • ACME-101 — Background export job 5 pts

    Moves the export off the request thread into a queued job. The heavy part isn't the queue — it's that the existing export code assumes it can stream to the response, and has to learn to write to storage and notify instead.

  • ACME-102 — "Your export is ready" email 1 pt

    The email with the download link. The mail template system already exists; this only adds one template and the trigger.

Front B — search

  • ACME-110 — Multi-field search with typo tolerance 5 pts

    The engine change: index title, owner and tags; rank matches; tolerate one edit of distance. This is the happy path — a search that finds things.

  • ACME-111 — The empty state 3 pts needs copy from design

    What the user sees when there are still no results: what was searched, the closest match, and how to broaden. If ACME-110 is "it finds", this is "it explains when it doesn't".

Carryover from cycle 11

  • ACME-095 — Smoke tests against staging 2 pts

    Automated checks against the real backend as a gate before production deploys. No product value visible, but it prevents the kind of breakage that already happened once.

The 2 decisions

Each with what's being decided, what happens under each option, and a recommendation.

decision 1 · capacity

Does ACME-111 (the empty state) ship in cycle 12 or 13?

What's being decided: whether the empty state is committed for these two weeks or the next two.

Why it's a question: 16 points for two weeks means something has to give. This is the natural candidate: it depends on ACME-110 by real dependency — they share components — and it's the one blocked on copy.

recommended — move to 13 Cycle 12 lands at 11 + 2 carryover

Front B keeps one ticket (the engine, 5 pts) and front A ships complete. One primary front, one secondary — the goal.

keep it in 12 Cycle 12 stays at 14 + 2 carryover

16 points, two parallel fronts. If something slips, it slips anyway — but you find out mid-sprint instead of now.

decision 2 · order of work

Which front starts first?

Why the order matters: the export job (front A) needs a queue worker deployed. If the worker deploys first, front A's two tickets flow back-to-back; if search starts first, the worker deploy interrupts it midway.

recommended Front A first

Deploy the worker once, ship both export tickets on top of it, then switch to search with no context left behind.

alternative Front B first

Search is the more visible win, but the worker deploy lands mid-front and forces a context switch.
