The case of the icons

This is "check" today in the admin app: seven different libraries for the same concept. That several look almost identical is exactly the problem — they are different assets, from different vendors, loaded separately to draw the same thing.

eva solar fluent lets-icons lucide mdi material

The proposal: a single, typed catalog on the solar set, which already covers 72% of what we use. With a browsable gallery in Storybook so nobody has to guess.

One concept, one icon. Using one outside the catalog will become a compile error.

What we're building

A layered design system — the same pattern as MUI, Shopify Polaris or GitHub Primer. Each layer is a package with its own release cadence.

publishedtokens

Colors, typography, shadows, borders. Pure data: even an email could use them.

augusticons

Single icon catalog and Icon component, with a browsable gallery.

augusttheme

Component styles: button variants, motion, per-component styling.

augustcomponents

Menu, MenuItem, section buttons, filters, each with its stories.

Proposed roadmap

The reference pace: everything done so far shipped in one week of work.

august

Platform, components and full theme

Single icon catalog with a visual gallery in Storybook (search the icon, copy the name, done), full theme (soft variants and component styles), system docs in the internal portal, first shared components with their stories, and automatic unification of duplicated icons into the canonical set across the codebase.

september

The second app joins

It replaces its copies with the design system and every fix is made once. Second wave of high-usage components lands: labels, cards, snackbar, loaders, avatars.

october +

Full coverage

The third app joins, the form engine is unified (two coexist today) and we measure system adoption per product.

How we work

Lightweight flow, no validation tickets.

Every change enters through a PR with peer review

The other developer reviews it — each dev reviews the other's PRs.

Every PR generates a Storybook preview

The designer opens it, sees the components rendered in all their variants and approves before merge.

Design owns everything visual

No value changes without design sign-off. Differences against the mockups are documented and design decides; automated before/after comparison tests verify nothing shifts visually.

Centralized docs

Flow, decisions and guides live in the internal docs portal and in Storybook. Anyone on the team can contribute, designers included.
